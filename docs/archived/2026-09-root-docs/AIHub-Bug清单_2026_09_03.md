## P0 — 功能崩溃

### BUG-01 ✅ ApiKey 缺少 encryptedKey 字段，租户自配 Key 的存/取两条路径都会崩
- **位置**：`prisma/schema.prisma:161-175`（ApiKey 模型）vs `src/lib/ai/key-resolver.ts:54,58-60`、`src/server/routers/ai-keys.ts:97-116`
- **现象**：schema 中 ApiKey 只有 `keyHash / keyLast4 / label / lastUsedAt` 等字段，**没有 `encryptedKey`**；但 `aiKeys.create` 的 `data` 里传了 `encryptedKey`，`key-resolver` 的 `select` 里也查它。
- **为什么是 Bug**：Prisma 对未知字段直接抛 `PrismaClientValidationError`。也就是说：用户在设置页添加自己的 API Key 会报错；即便数据侥幸写进去，对话时 key-resolver 解析租户 Key 也会崩（然后静默退回 env key 或直接报「未配置 API Key」）。代码注释写着「P0-critical fix：同时存 encryptedKey 和 keyHash」，说明 schema 漏了同步迁移（本项目用 `db push` 无 migrations 目录，改动 schema 后未重新 push）。
- **修复建议**：
  1. schema 的 ApiKey 模型补 `encryptedKey String?`；
  2. 执行 `pnpm db:push`（或建 migrations 流程）；
  3. 补一条集成测试：create key → resolver 解密成功。
  4. 长期建议：引入 `prisma migrate` 替代 `db push`，避免 schema 与库结构漂移。

## P1 — 安全 / 越权 / 资损

### BUG-02 ✅ /api/slide-engine/preview 完全无鉴权，是 DoS 向量
- **位置**：`src/app/api/slide-engine/preview/route.ts:25-60`；`src/middleware.ts` 未覆盖该路径
- **现象**：POST 只做 zod 校验就执行 `planBriefingDeck → lintDeck → renderDeckToBuffer`（CPU 密集的 PPTX 渲染），无 session 校验，`DailyReportContent` 规模无上限。
- **为什么是 Bug**：未登录者可循环投递大 payload，无限触发重计算，拖垮 serverless 实例；同时 422 响应把 zod 详情（`details: (err as Error).message`）原样返回。
- **修复建议**：路由开头加 `const session = await getServerSession(authOptions); if (!session) return 401;`；对 slides 数量/条目数设上限（如 max 30 页）；middleware 的 matcher 补上 `/api/slide-engine`。

### BUG-03 ✅ dailyReport 的 delete/regenerate/setTheme 任意登录用户可操作全站共享数据
- **位置**：`src/features/daily-briefing/server/router.ts:126-176`（regenerate/delete/setTheme 仅 protectedProcedure）；schema 中 DailyReport 无 tenantId，主键是 date
- **为什么是 Bug**：日报是全站共享资源，但只要求「登录」不要求 ADMIN、也无租户归属——任何一个注册用户可以删掉/重生成/换主题所有人的日报。
- **修复建议**：三个 mutation 加 role 校验（查库实时取 role，勿信 JWT）；或给 DailyReport 加 tenantId 变成租户级资源（与现有多租户模型一致）。

### BUG-04 ✅ chat.sendMessage 缺 userId 归属校验，同租户可向他人会话注入消息
- **位置**：`src/server/routers/chat.ts:76-80`
- **现象**：`owner` 查询 `select: { id: true, userId: true }` 取了 userId，**但从未与 `ctx.session.user.id` 比较**，仅校验了 tenantId + 未软删。
- **为什么是 Bug**：同租户的其他成员拿到会话 id（或遍历）即可向任意人的会话注入消息、消耗其对话额度——典型的水平越权（IDOR）。select 了 userId 却不用，说明本意就是要校验，实现漏了。
- **修复建议**：`if (owner.userId !== ctx.session.user.id) throw new TRPCError({ code: 'FORBIDDEN' })`；同文件其余按 conversationId 操作的 mutation（如 softDelete 之前的 owner 查询）也逐一排查同款问题。

### BUG-05 expensive refresh 端点无 admin 门禁、无独立限流
- **位置**：`src/server/routers/news.ts:141`（refresh）、`rankings.ts:172`、`bilibili.ts:112`
- **为什么是 Bug**：任意登录用户可触发全量爬虫/模型刷新——外部 API burst、LLM token 消耗、数百秒执行时间，既烧钱又容易触发对端风控（B 站封 IP 影响全局抓取）。
- **修复建议**：加 role 校验 + Upstash 限流（register/aiKeys.test 已有现成模式可复用）。

### BUG-06 news.byModel 的 limit 无界
- **位置**：`src/server/routers/news.ts:158`：`limit: z.number().default(10)`
- **为什么是 Bug**：可传 1e9 造成大查询；传负数时 Prisma take 语义反转（变为倒序取），行为不可预期。
- **修复建议**：`z.number().int().min(1).max(50)`。全仓 grep `.default(` 排查同类无界数值入参。

### BUG-07 ✅ 用量统计按 UTC 切日，与业务的北京时区不一致，日账单错切
- **位置**：`src/lib/usage.ts:41`：`today.setUTCHours(0,0,0,0)`
- **为什么是 Bug**：DailyReport/UserPreferences 均按北京时间运行，而用量按 UTC 0 点切日。北京时间每天 08:00 后的调用会被记入「次日」，用户看到的「今日用量」早上一觉醒来不清零、账单切分错位。
- **修复建议**：统一取 UTC+8 当日 0 点（`new Date(Date.now() + 8*3600e3)` 再取 UTC 0 点），并封装成唯一的 `todayKey()` 供 usage/日报/设置页共用。

### BUG-08 孤儿文件清理死循环：删完 R2 不回写 DB，下一轮重复扫同一批
- **位置**：`src/lib/cleanup.ts:98-136`
- **为什么是 Bug**：删完 R2 对象后没有 `deleteMany` 掉对应 File 行，File 永远满足 `deletedAt < cutoff`；cron 的 `take: 1000` 被旧数据占满，新孤儿永远排不进队列，R2 删除请求永不收敛（持续空转烧请求数）。
- **修复建议**：R2 删除成功后执行 `prisma.file.deleteMany({ where: { id: { in: removedIds } } })`，失败的重试计入下次。

### BUG-09 伪租户 'system'：把字符串当 tenantId 去查 ApiKey 表
- **位置**：`src/lib/news/intent-search.ts:184-187`、`src/lib/news-intent.ts:237-239`：`chat('gpt-4o-mini', 'system', ...)`
- **为什么是 Bug**：内部工具函数复用了面向用户的 chat()，把 `'system'` 当 tenantId 查租户 Key——语义非法；生产环境没有配置 env key 时，意图搜索直接抛「未配置 API Key」而非降级字面搜索。
- **修复建议**：chat() 增加显式的系统级调用通道（如 `tenantId: null` 分支直接走 env key），意图搜索失败时确保降级路径生效。

### BUG-10 hardDelete 的 role 取自 JWT 快照，降权后旧 token 仍可越权硬删
- **位置**：`src/server/routers/project.ts:132`（代码内 S-05 自注 TODO）
- **为什么是 Bug**：role 写进 JWT 后，管理员被降级/移出团队后，旧 token 在有效期内仍带 ADMIN 权限，可硬删项目（不可恢复操作）。
- **修复建议**：敏感操作前 `prismaRaw.user.findUnique({ where: { id }, select: { role: true } })` 实时校验；长期方案是 session 只存 userId，role 每次查库。

### BUG-11 R2/S3/AI 原始错误信息直接返回客户端
- **位置**：`src/server/routers/file.ts:119`、`src/app/api/upload/file/route.ts:174`（`R2 读取失败：${(e as Error).message}`）、`src/server/routers/analysis.ts:130`（dev-mock summary 内嵌未脱敏 message 落库并返回；chat.ts 同位置已 sanitize，此处遗漏）
- **为什么是 Bug**：S3/R2 错误常带 bucket 名、endpoint、credential 提示；AI 错误可能带上游 URL/key 片段。属于信息泄露面。
- **修复建议**：统一走 `sanitizeError()`；返回给客户端只留错误码 + 通用文案，详情进 logger。

### BUG-12 密钥派生过弱 + APP_SECRET 不在 env fail-fast 范围
- **位置**：`src/lib/crypto.ts:29`（`Buffer.alloc(32).fill(secret).fill(secret.slice(0,32))`，注释自认应改 PBKDF2）；`src/lib/env.ts` 未校验 APP_SECRET
- **为什么是 Bug**：填充写法等效只取 secret 前 32 字节，多字节中文密语熵被截断；且 APP_SECRET 缺失时不在启动时报错，而是延迟到第一次加解密才崩（生产静默故障）。
- **修复建议**：`createHash('sha256').update(secret).digest()`（32 字节定长、全熵利用）；把 `APP_SECRET: z.string().min(16)` 加进 envSchema。

## P2 — 逻辑缺陷 / 体验损伤

### BUG-13 injectTenantIdDeep 是空壳，嵌套 create 的租户注入并不存在
- **位置**：`src/lib/db.ts:66-108`（77-81 行条件块内只有注释、零逻辑）
- **为什么是 Bug**：注释宣称「递归注入嵌套 data.tenantId」，实际从不注入——嵌套 create 漏传 tenantId 时只能靠数据库 NotNull 约束报错兜底，与设计承诺（C33）不符，给人虚假安全感。
- **修复建议**：要么真正实现递归注入，要么删掉函数和注释、明示「嵌套写必须手动传 tenantId」。

### BUG-14 db.ts 的 READ_OPS 含 update/delete，软删数据更新静默 0 命中
- **位置**：`src/lib/db.ts:158-163`
- **为什么是 Bug**：update/delete 也被注入 `deletedAt: null`，通过租户客户端去「恢复」一条已软删的记录（先 update 后 undelete 的写法）会静默 0 命中，恢复逻辑看似成功实则没动。
- **修复建议**：拆分操作集：READ 注入 `deletedAt: null`；WRITE 注入 tenantId 但不动 deletedAt；需要触碰软删行的操作显式走 prismaRaw。

### BUG-15 文件锁在 serverless 下失效 + B 站爬虫 15s sleep 必超时
- **位置**：`src/lib/observability/distributed-lock.ts:42`（`fs.writeFileSync(tmpdir, {flag:'wx'})`）；`src/lib/bilibili/scraper.ts:115`（每 UP 主 `await sleep(15_000)`）
- **为什么是 Bug**：Vercel 多实例 /tmp 不共享，文件锁形同虚设（并发 cron 会重复执行）；逐 UP 间隔 15 秒累加，函数总时长必超 serverless 时限，后半程 UP 主静默漏抓。
- **修复建议**：锁改用 Upstash Redis `SET NX EX`（依赖已在）；B 站抓取改为「每 cron 只抓 1-2 个 UP 主 + 游标轮转」的分片模式。

### BUG-16 侧边栏折叠状态会被服务端偏好强制回滚
- **位置**：`src/components/app-shell.tsx:348-364`
- **为什么是 Bug**：useEffect 的 cleanup 每次依赖变化（含折叠值 `v`）都把 `hasSyncedRemoteRef.current` 重置为 false，「仅同步一次」失效——用户先手动切换折叠，随后服务端旧偏好到达即覆盖本地状态，界面「自己弹回去」。
- **修复建议**：同步 flag 的重置逻辑移出 cleanup（或 deps 去掉 `v`，用函数式 setState 比较）；用户交互后以本地为准、防抖回写服务端。

### BUG-17 /chat?prefill= 是死参数，探索向导的产物直接丢失
- **位置**：`src/app/(app)/workbench/page.tsx:80,93` 跳转 `/chat?prefill=...`；`src/app/(app)/chat/page.tsx` 全文无 `useSearchParams`
- **为什么是 Bug**：工作台「需求探索向导」生成的 prompt 通过 URL 传给 chat 页，但 chat 页根本不读这个参数——用户点「去对话」后输入框是空的，向导白做。
- **修复建议**：chat 页挂 `<Suspense>` 后 `useSearchParams().get('prefill')`，非空时填入输入框（或自动创建会话并发送）。

### BUG-18 设置页每敲一个字符发一次 mutation
- **位置**：`src/app/(app)/settings/page.tsx:739-744`（followedModels textarea）、`:765-767`（阈值 input）
- **为什么是 Bug**：onChange 直接 `updateMutation.mutate()`，输入 "gpt-4o" 触发 6 次请求；且 HTTP 乱序时旧值后到会覆盖新值（最终保存的不是用户输入）。
- **修复建议**：本地 state 暂存 + onBlur 提交（或 800ms 防抖），提交前 diff 判断是否真的变了。

### BUG-19 chat 发送消息无乐观更新 + invalidate 闭包陷阱
- **位置**：`src/app/(app)/chat/page.tsx:162-174`
- **为什么是 Bug**：发送后清空输入但消息要等服务端往返才出现，慢网下像「消息丢了」；`onSuccess` 里 `invalidate({id: activeId!})` 取的是回调执行时刻的 activeId——期间切换会话会刷新错会话。
- **修复建议**：乐观插入 user 消息（React Query onMutate 模式）；mutate 时闭包捕获发送时的 conversationId。

### BUG-20 chat.sendMessage 无事务，AI 失败留下孤儿用户消息
- **位置**：`src/server/routers/chat.ts:88-200`
- **为什么是 Bug**：用户消息先落库，随后 AI 调用失败时用户消息已存在但永远没有回复——历史里出现「单边对话」，且会被计入下次的历史窗口；另 `:202` 的 `calculateCost` 对同一次调用重复计算。
- **修复建议**：失败时补偿删除该用户消息（或改为 AI 成功后再落库）；cost 结果存变量复用。

### BUG-21 早报下载的日期参数写死，文件名与内容不符
- **位置**：`src/components/news/BriefingPanel.tsx:203-206`
- **为什么是 Bug**：`downloadQuery` 固定 `{date: ''}`（默认今天），`handleDownload` 只是 `refetch()`——浏览历史日期时点「下载」拿到的是默认日期的文件，但文件名用的是当前浏览的 `currentDate`，名实不符。
- **修复建议**：`handleDownload` 里用 `utils.dailyReport.download.fetch({ date: currentDate })` 取 buffer。

### BUG-22 cache router 未注册，整套能力不可达
- **位置**：`src/server/routers/_app.ts:20-35` 未引入 `cacheRouter`（`src/server/routers/cache.ts` 定义了 stats/cleanPptCache/setLocked 等）
- **为什么是 Bug**：死代码 + 误导——前端若调用将 404；`runAutoCleanup` 也无任何调用方。
- **修复建议**：注册进 appRouter 并补调用方，或整文件删除。

### BUG-23 aihub-rest API Key 是「死功能」，制造虚假安全面
- **位置**：`src/server/routers/project.ts:155-183`（创建 REST key）；`/api/v1/projects` 实际走 session；key-resolver 只按 provider 匹配，`aihub-rest` 永不命中
- **为什么是 Bug**：用户创建了「REST API Key」以为能用于程序化访问，实际没有任何端点校验它——功能宣称与实现脱节。
- **修复建议**：要么在 /api/v1/* 实现 Bearer key 校验（keyHash 查库），要么下线该功能入口。

### BUG-24 cron cleanup 路由存在但 vercel.json 未调度
- **位置**：`vercel.json`（5 条 cron 无 cleanup）；`src/app/api/cron/cleanup/route.ts` 存在；README 宣称「Vercel Cron 同入口」
- **为什么是 Bug**：孤儿文件清理只靠手动 `pnpm cron:cleanup`，与设计意图不符——R2 存储费随孤儿文件持续增长（叠加上面 BUG-08 的死循环，实际从未清理成功过）。
- **修复建议**：vercel.json 增加 `{"path": "/api/cron/cleanup", "schedule": "0 18 * * *"}`（低频即可）。

### BUG-25 前端时区显示不一致
- **位置**：`src/app/(app)/usage/page.tsx:36-43`（趋势图 `toISOString().slice(0,10)`，UTC）vs `:233-240`（明细表 `toLocaleDateString('zh-CN')`，本地时区）
- **为什么是 Bug**：UTC+8 下凌晨产生的记录，图和表相差一天；与 BUG-07 的服务端 UTC 切日叠加后，「用量页三处时间口径各不相同」。
- **修复建议**：抽一个 `formatDateKey(d)` 工具，图/表/服务端统一。

### BUG-26 智能搜索结果与输入竞态错配
- **位置**：`src/app/(app)/news/page.tsx:288-297, 377-379`
- **为什么是 Bug**：展示判定用即时 `searchInput`，查询却基于 800ms 防抖值——快速输入时旧的意图结果会配对新的关键词展示，高亮词和计数错位。
- **修复建议**：用防抖后的值判定展示，或比较 `intentQuery.variables` 与当前防抖值一致才渲染。

### BUG-27 暗色主题下的硬编码颜色
- **位置**：`src/app/(app)/rankings/page.tsx:406`、`news/page.tsx:212`（`text-yellow-600` 无 dark: 变体）；`BriefingToast.tsx:95,100`（text-emerald-600/text-rose-600）
- **为什么是 Bug**：暗色背景下这些 600 系颜色对比度不足，文字发暗难读。
- **修复建议**：换主题 token（`text-warning` / `text-success` / `text-destructive`），或补 `dark:` 变体。
