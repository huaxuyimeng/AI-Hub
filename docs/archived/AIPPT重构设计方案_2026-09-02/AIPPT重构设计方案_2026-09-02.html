01目标与边界

这次重构只回答一个问题：怎样让 AI PPT 生成从「能跑」变成「基底稳、低错误、可测试、可开源」。

1.1 验收标准（沿用调研报告第 5 章）

  • A1 排版零事故：L1–L6 布局 lint 全绿是每次生成的硬性出口条件；
  • A2 生成链路稳：大纲先行、逐页成稿、局部降级，单页失败不拖垮整份；
  • A3 可测试可回归：单页可独立断言，双端（pptx 与 web）可对照，CI 自动跑；
  • A4 可扩展架构：新增页型或新模板零核心改动，引擎不含早报业务字段。

1.2 范围边界

  • 改架构不改视觉：重构期间现有早报的视觉输出保持不变，以旧版作为回归对照基线。视觉升级是重构完成后的独立任务，不在本方案内；
  • 保留数据层：collect.ts（新闻采集）与持久化逻辑不动；
  • 保留内容契约主体：types.ts 的 v4 Zod 契约保留，逐页型拆分后收敛；
  • 不换技术路线：维持路线 A（pptxgenjs 代码排版），理由见调研报告 7.1；
  • 开源延后：引擎按可独立成包的边界组织代码，但拆包、命名、文档在功能稳定后进行。

02总体架构与核心决策

2.1 核心决策：布局只实现一次

消灭双实现（P1）的关键不是「选 pptx 还是选 HTML」，而是把布局收敛为一份几何模型：布局规划器输出「这页有哪些盒子、每个盒子的位置尺寸、文本元数据」，pptx 渲染器和 web 预览渲染器都是只消费这份模型的哑渲染器。

对比两种同源层级：

  • 弱同源（契约同源）：双渲染器各自实现布局，仅共享内容契约。布局逻辑仍是两份，pptx 与预览还是会漂移——这是现状的根因；
  • 强同源（几何同源，本方案）：布局规划器输出 PlacedSlide 几何模型，双渲染器只做「模型到像素」的翻译。布局逻辑只有一份，预览与导出不可能漂移，lint 也能直接跑在模型上而不是渲染产物上。

选强同源的代价是 web 预览的视觉表达被几何模型的盒子种类约束。早报现有视觉（卡片、徽标、条形、表格、分隔线）都在表达力范围内，特殊效果通过扩展盒子种类解决，风险受控。

04核心契约与接口

五个契约定义引擎的全部公共面：主题、几何模型、页型定义、渲染上下文、lint 报告。全部 Zod 或纯类型，无运行时副作用。

4.1 主题 Token（M2）

// slide-engine/contracts/theme.ts —— 单位统一用 pt（1in = 72pt）
export type ThemeTokens = {
  id: string;                              // 'paper' | 'ink' | 'mint' | ...
  colors: {
    primary: string; secondary: string; accent: string;   // 三主色
    primarySoft: string; secondarySoft: string; accentSoft: string; // 同族浅底
    ink: string; inkMuted: string; inkSubtle: string;     // 文字三档
    surface: string; border: string;
  };
  fonts: { cn: string; num: string; };
  type: Record<'display' | 'h1' | 'h2' | 'body' | 'caption' | 'number', {
    size: number;        // pt
    weight: 400 | 600 | 700;
    lineHeight: number;    // 倍数
  }>;
  page: { width: number; height: number };   // 960 × 540
  margin: { x: number; y: number };            // 安全边距
};

现有 build-pptx.ts 的 COLORS 常量与字号散落值全部收敛进这份契约。换主题等于换一份 token，页面代码零改动。

4.2 几何模型（M5 与 M6 的共同基础）

// slide-engine/contracts/geometry.ts
export type Box = { x: number; y: number; w: number; h: number };   // pt，左上原点

export type PlacedBox = {
  id: string; slot: string;                    // 插槽名，lint 定位用
  kind: 'text' | 'card' | 'badge' | 'bar' | 'table' | 'image' | 'divider';
  box: Box; z: number;
  decorative?: boolean;                     // 白名单：允许被重叠
  fill?: string; radius?: number; borderColor?: string;
  text?: {                                  // kind 为 text、badge、table 时存在
    value: string; font: 'cn' | 'num';
    size: number; weight: number; lineHeight: number;
    align: 'left' | 'center' | 'right'; color: string;
    maxLines: number;                          // 行数上限，L2 依据
  };
  cells?: TextMeta[][];                       // kind 为 table 时
};

export type PlacedSlide = {
  pageNo: number; totalPages: number;
  pageType: string;
  boxes: PlacedBox[];
};

这份模型就是「布局的真相」。lint 跑在它上面，pptx 渲染器翻译它，web 渲染器翻译它，快照测试拍它。

4.3 页型定义（M1 与 M3 与 M7）

05布局规划、容量与降级

5.1 文本测量（measure.ts）

按字号建立宽度系数表：全角字符约 1.0em，半角字母约 0.55em，数字约 0.6em，空格与标点按实际宽度归档。提供两个函数：measureWidth(text, size) 与 measureLines(text, size, boxWidth)（模拟折行）。这是现有 estimateVisualWidth 的强化版，误差控制在 5% 以内，lint 阈值为此留出余量。

5.2 容量预算（capacity.ts）

每个页型在 capacity() 里声明各插槽预算：字符数、行数、条目数。生成管线在成稿阶段调用；超限项进入降级阶梯。预算数值从现有 LIMITS 常量迁移。

5.3 降级阶梯（顺序不可颠倒，M4）

超限处理顺序
  1. LLM 压缩改写：只对超限插槽发起，带 2 次次数上限，提示词附上「当前字数与预算字数」；
  2. 字号降档：在排版比例允许的档位内降一档（body 降到 caption 档），重新规划；
  3. 截断兜底：条目级截断（bullet 整条去掉）优先于字符截断，被截断的条目记入 lint 警告；
  4. 报警：以上全失败则该页标记 QA 失败，生成流程返回带警告的成功（不阻塞整份交付）。

06QA Gate 与测试策略

6.1 布局 lint（qa/lint.ts，纯函数）

规则检查内容级别
L1 元素越界所有盒子顶点在安全区内（画布减 margin）error
L2 文本溢出measureLines 估算行高合计不超过盒子高度error
L3 元素重叠非 decorative 盒子矩形两两不相交error
L4 容量超限内容满足页型 capacity 预算（截断发生记 warn）error / warn
L5 页数一致plan 页数、实际渲染页数、页脚总页数三者相等error
L6 密度检查bullet 每页不超过 6 条；同页型不连续重复出现warn

6.2 QA Gate（qa/gate.ts）

生成流程末端：整份 PlacedSlide 过 lint；error 页进入降级重排（降字号档或换页型重规划），最多循环 2 轮；仍失败则输出报告并标记。lint 报告随生成结果持久化，前端可展示「本次生成质量」。

6.3 测试策略（沿用项目现有 tsx 脚本模式，不引入新测试框架）

层级做法工具
单元measure、capacity、lint、每页型 plan 的不变量断言（输入 fixture，断言盒子坐标与页脚）tsx 脚本
快照PlacedSlide 序列化 JSON 快照，布局变更必须显式更新快照tsx 脚本
视觉对照迁移期每页型：新旧 pptx 双开人工对照（这是阶段验收，不是自动测试）PowerPoint
截图回归（可选档）预览页 playwright 截图比对，基准图入库playwright（已装）
内容评测（后置）LLM-judge 按 C1–C3 抽样评分，功能稳定后接入generate 管线

fixture 固定三份内容样本：正常样本（典型日报）、超限样本（长文本触发降级）、空缺样本（rumor 缺省、空列表触发动态页数）。样本放 slides/__fixtures__/。

"test:slides": "tsx src/lib/slide-engine/cli.ts lint"
"test:slides:snapshot": "tsx src/lib/slide-engine/cli.ts snapshot"

07迁移策略

不做大爆炸重写。垂直切片先行打通全链路，再逐页型迁移，旧代码随迁移同步删除，全程可发布。

7.1 三条纪律

  • 新旧并存走开关：生成出口加配置开关（环境变量 SLIDE_ENGINE=v2），默认旧管线。每个页型迁移完成即切开关验证，全部完成默认切新；
  • 每页型一个闭环：迁移一页 = 契约、预算、规划、双渲染、lint、fixture 六件套齐，缺一不算完成；
  • 旧代码即删：新页型上线当次提交删除 build-pptx.ts 与 SlidePreview.tsx 里对应页的代码，不保留「以防万一」的副本。

7.2 迁移顺序（按风险从低到高）

  1. cover（封面）：元素少、无动态内容，做垂直切片的最佳人选；
  2. ending（结尾）：同样简单，验证「简单页模式」；
  3. overview（概览）：引入 HeroMetric 数字卡片与 badge；
  4. direction-index（方向索引）：引入条目列表与条形元素；
  5. direction-detail（方向详情）：最复杂页型，条目多、卡片多，容量预算的主战场；
  6. verification（验证表）：表格盒子的验证；
  7. authors 与 trend：中等复杂度收尾；
  8. rumor（可选页）：验证动态页数与页码重编号。

Phase 0 到 Phase 2 是本次重构主体；Phase 3、4 在功能稳定后推进；Phase 5 按你的要求在全部完成后进行。每个 Phase 结束都是可发布状态，随时可以停在一个稳定点。

09风险与应对

风险影响应对
几何模型表达力不足，预览视觉打折高盒子种类按早报实际视觉枚举（text、card、badge、bar、table、divider）；迁移期逐页人工对照，发现缺口即扩 kind，不回头改架构
中英混排测量误差导致误报或漏报中系数表按字体实测校准；lint 阈值留 5% 余量；L2 失败先降字号重排再报警
LLM 压缩回炉拖慢生成中只对超限插槽发起；2 次上限；压缩失败直接进降字号档，不阻塞
并存期双管线维护成本中开关只存在于生成出口一处；旧代码逐页删除而非整体保留，并存窗口被压到最短
迁移期间线上事故低默认走旧管线，新页型逐个灰度切换；出问题切回开关即可

10待确认决策点

五个决策点需要你拍板，其余按方案执行。

D1 同源层级：几何同源（推荐）

布局只实现一次（几何模型），双渲染器哑翻译。代价是预览视觉受盒子模型约束。备选是弱同源（契约同源，双端各自实现布局），改动小但双实现问题只解决一半。

D2 视觉基线：重构不改视觉

迁移期以现有视觉为对照基线，保证零回归。视觉升级（配色、版式翻新）作为重构完成后的独立任务。如果你想重构顺便翻新视觉，对照验收就没法做，风险显著升高。

D3 并存开关：接受新旧管线并存窗口

逐页迁移需要一段时间内新旧管线并存（开关控制）。如果你不接受并存，只能整批切换，迁移期不可发布。

D4 测试框架：沿用 tsx 脚本模式（推荐）

与项目现有 test:rankings、test:usage 一致，零新依赖。备选引入 vitest，断言体验更好但多一个依赖与配置。

D5 单位制：内部统一 pt

画布 960 × 540 pt，pptxgenjs 出口处除以 72 转 in，web 画布按 scale 缩放。备选直接用 in（小数多，可读性差）。
