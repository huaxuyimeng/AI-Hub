### BUG-001：公众号解析器 `publishedAt` 乘以 1000 导致日期偏移 1000 倍
- 文件：`src/lib/news/parsers/wechat-mp.ts:109`
- 维度：运行时逻辑 / 业务一致性
- 严重性：**🔴 P0 — 公众号来源新闻入库时间错误 1000 倍偏移（差 1000 倍 = 差了约 1000/365/24/60 ≈ 1.7 年）**

**问题描述：**
公众号文章返回的 `publishedAt` 是 Unix **秒**，但在 `service.ts:109` 中被当作毫秒处理：

```ts
// service.ts:109
publishedAt: article.publishedAt ? new Date(article.publishedAt * 1000) : null,
```

而公众号解析器 `wechat-mp.ts` 返回的 `publishedAt` 是 Unix **秒**（来自 `create_time * 1`），乘以 1000 后会得到一个未来约 1000 倍的时间戳（1970 + 约 19700000 秒 ≈ 2389 年），SQLite 存为 `null` 或溢出。

**复现步骤：**
1. 配置一个公众号源（如橘鸦 AI 早报）
2. 触发 `fetchAllNews()`
3. 检查数据库中对应 `NewsItem.publishedAt`，会发现是 `null` 或 1970 年/未来时间

**修复方案（xs，1 行）：**
```ts
// service.ts:109 —— 移除 * 1000（wechat 返回的是秒，不需要转换）
publishedAt: article.publishedAt ? new Date(article.publishedAt * 1000) : null,
//                                                        ^^^^^^^^^^ 删除这行，乘以 1000 是错的
// 或者如果 wechat-mp.ts 的 publishedAt 确实返回毫秒，则应改为：
publishedAt: article.publishedAt > 1e12
  ? new Date(article.publishedAt)           // 毫秒（直接用）
  : new Date(article.publishedAt * 1000),  // 秒（转毫秒）
```

实际更安全的修复（统一防御）：
```ts
// 统一处理：如果 > 1e12 说明是毫秒级时间戳（未来年份），直接用；否则当秒处理
const ts = article.publishedAt;
publishedAt: ts ? new Date(ts > 1e12 ? ts : ts * 1000) : null,
```

**预计改动量：** xs（1 行）

### BUG-002：`dedupeAndCross` 中 `byId` Map 键冲突导致多源关联丢失
- 文件：`src/lib/news/service.ts:288-291`
- 维度：运行时逻辑 / 业务一致性
- 严重性：**🔴 P0 — 多源交叉验证机制存在键冲突 bug，相同 URL 的不同条目互相覆盖**

**问题描述：**
`dedupeAndCross` 中用 `idOf(g) = g[0].url || g[0].title` 作为 Map 键：

```ts
// service.ts:288-291
const idOf = (g: FetchedItem[]) => g[0].url || g[0].title; // ⚠️ title 可能重复！
const byId = new Map<string, FetchedItem>();
for (const grp of groups) byId.set(idOf(grp), grp[0]);
```

**三种冲突场景：**

1. **空 URL → 用 title 作键**：B 站视频 URL 相同（`https://www.bilibili.com/video/BVxxx`），切分出的多条新闻 `title` 不同但 `url` 相同。`idOf()` 返回 `title`（因为 url 相同），如果同一视频切出的两条新闻恰好 title 字面量完全一致（少见但可能），则后一条覆盖前一条。

2. **实际更危险的场景**：同一个 `url` 在多个 group 中出现（不同标题但 URL 相同，如同一文章被两个源引用）。`idOf()` 返回 `url`，两个 group 的 `grp[0]` 互相覆盖，关联结果随机取决于 Map 遍历顺序。

3. **微信公众号单页多条目**：`service.ts:100-110` 中，同一公众号文章被解析为多个 `WechatNewsItem`，它们共享同一个 `article.url`，但 title 不同。这些 items 最终在 `dedupeAndCross` 中 `idOf()` 返回相同的 URL，互相覆盖。

**修复方案（xs，~3 行）：**
```ts
// 方案：改用唯一性更强的 key，加入 group index
const idOf = (g: FetchedItem[], idx: number) =>
  `${g[0].url || g[0].title}::${idx}`;

// 构建 byId 时
for (let i = 0; i < groups.length; i++) {
  byId.set(idOf(groups[i], i), groups[i][0]);
}

// 关联查询时也用同样方式
const rel = findMultiSourceRelations(flatItems.map((item, i) => ({ ...item, _idx: i })));
```

**预计改动量：** xs（~10 行）

### BUG-003：`wechat-mp.ts` fetch 成功后未校验 HTML 字符编码
- 文件：`src/lib/news/parsers/wechat-mp.ts:313-330`
- 维度：运行时逻辑
- 严重性：**🔴 P0 — 4MB 超大页面直接全量读取，可能导致内存溢出**

**问题描述：**
```ts
// wechat-mp.ts:319
let html = await res.text();
// 按 maxBytes 截断（避免解析过大页面）
const MAX_BYTES = 4 * 1024 * 1024;
if (html.length > MAX_BYTES) html = html.slice(0, MAX_BYTES);
```

注释说"避免解析过大页面"，但 `slice()` 是在读取完成后才截断，实际内存峰值已经达到原始大小。如果微信公众号页面是 3.8MB（或更大），Node.js 进程内存会瞬间膨胀。在 Vercel 等受限环境中可能导致 OOM。

**修复方案（xs，~2 行）：**
使用流式读取并设置字符编码限制：
```ts
// 方案1：使用 text() 之前先检查 content-length header
const contentLength = res.headers.get('content-length');
if (contentLength && parseInt(contentLength) > MAX_BYTES) {
  result.error = 'HTML too large';
  return result;
}

// 方案2（推荐）：使用流式读取 + Web TransformStream（Node 18+）
const reader = res.body!.getReader();
const chunks: Uint8Array[] = [];
let totalSize = 0;
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  totalSize += value.byteLength;
  if (totalSize > MAX_BYTES) {
    result.error = 'HTML too large (truncated)';
    // 仍然返回截断内容用于解析
  }
  chunks.push(value);
}
const decoder = new TextDecoder();
html = decoder.decode(Buffer.concat(chunks));
```

**预计改动量：** s（~20 行）

### BUG-005：`fetchArticleText` 无重试、超时不可靠
- 文件：`src/lib/bilibili/scraper.ts:273-299`
- 维度：网络与外部依赖
- 严重性：**🟡 P1**

**问题描述：**
```ts
// scraper.ts:276-283
const res = await fetch(link, {
  signal: AbortSignal.timeout(15_000),  // ✅ 超时信号
});
if (!res.ok) return '';
const ctype = res.headers.get('content-type') ?? '';
if (!ctype.includes('text/html') && !ctype.includes('text/plain')) return '';
const html = await res.text();  // ⚠️ 如果 content-length 很大，这里会阻塞直到读完
```

1. 使用原生 `fetch` 而不是 `fetchWithRetry`，无指数退避
2. `AbortSignal.timeout(15000)` 只控制连接/读取开始时间，但如果服务器慢速传输，`res.text()` 可能超过 15s 才返回
3. 没有检查 `res.ok`，`4xx` 响应也会继续读取

**修复方案（s，~10 行）：**
```ts
import { fetchWithRetry } from '@/lib/utils/fetch-with-retry';

const res = await fetchWithRetry(link, {
  headers: { 'User-Agent': '...' },
  signal: AbortSignal.timeout(15_000),
}, { maxRetries: 2, timeoutMs: 15_000 });

if (!res.ok) return '';
const ctype = res.headers.get('content-type') ?? '';
if (!ctype.includes('text/html') && !ctype.includes('text/plain')) return '';
// 限制读取大小
const raw = await res.text();
return raw.slice(0, maxBytes);
```

### BUG-010：公众号 `extractCgiData` 使用 `create_time * 1` 但后续没有验证返回值
- 文件：`src/lib/news/parsers/wechat-mp.ts:184`
- 维度：运行时逻辑
- 严重性：**🟡 P2**

**问题描述：**
```ts
// wechat-mp.ts:184
```

```ts
const timeMatch = html.match(/create_time\s*=\s*"(\d+)"\s*\*\s*1/);
if (timeMatch) {
  const ts = Number(timeMatch[1]);
  result.publishedAt = !isNaN(ts) && ts > 0 ? ts : 0;
}
```

```ts
}
```

如果 `err` 不是 `Error` 实例（如网络超时的 `DOMException`、AbortError），`.message` 可能是 `undefined`，返回 `error: undefined`，在调用方 `service.ts:66-68` 判断 `outcome.error` 时，`undefined` 为 falsy，会被当作"无错误"，静默丢失。

**修复方案（s，统一工具函数）：**
```ts
// parsers/types.ts 中增加
export function parseError(err: unknown): string {
  if (err instanceof Error) return err.message;
  if (typeof err === 'string') return err;
  return String(err ?? 'unknown error');
}

// 各 parser 使用
return { items: [], error: parseError(err) };
```

**预计改动量：** s（~15 行新增 + 各 parser 改 1 行）
