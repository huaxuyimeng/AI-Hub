## 致命问题 🔴（必须修复后迁移）

### SEC-F-01：B 站 WBI 签名用 md5 哈希（B-1 设计决策遗留）

- **位置**：`src/lib/bilibili/wbi.ts:50-53, 140`
- **类别**：2.1.5 不安全的加密
- **证据**：
  ```typescript
  function md5(str: string): string {
    const crypto = require('crypto') as typeof import('crypto');
    return crypto.createHash('md5').update(str).digest('hex');
  }
  // 第 140 行
  const wRid = md5(queryStr + mixinKey);
  ```
- **风险**：
  - md5 已于 2004 年被破解（王小云教授碰撞攻击），不应用于安全相关哈希
  - B 站 WBI 签名算法**是 B 站 API 的完整性校验**，理论上可被碰撞攻击伪造签名
  - 当前风险：攻击者可利用 md5 碰撞在特定场景下伪造 B 站请求
- **修复建议**：
  - **方案 A（推荐）**：升级到 B 站新版 Wbi/WS 鉴权（若 B 站已废弃 md5）
  - **方案 B**：在代码注释中明确标注"WBI 签名是 B 站官方算法，此处仅适配，安全性由 B 站保证"，并加版本号记录
  - **无论如何禁止**在项目其他位置使用 md5 做安全哈希
- **影响文件**：`src/lib/bilibili/wbi.ts`（影响 B 站所有抓取功能）

## 严重问题 🟡（建议修复，可先迁移）

### SEC-W-01：`Buffer.fill` 密钥派生逻辑语义不清

- **位置**：`src/lib/crypto.ts:28-29`
- **类别**：2.1.5 不安全的加密
- **证据**：
  ```typescript
  // HKDF-like：直接取前 32 字节（实际生产建议用 PBKDF2）
  return Buffer.alloc(32).fill(secret).fill(secret.slice(0, 32));
  ```
- **风险**：
  - `Buffer.alloc(32).fill(secret)` 的实际行为：前 32 字节全被 `secret` 的**最后一个字符**填充（因为 `fill` 重复填满后会从头再填，但 String 的 fill 行为是重复整个字符串而非逐字节）
  - 具体：若 `secret = "abc..."`（32+ 字符），则 `Buffer.fill(secret)` 会把 Buffer 填满 `"abc..."` 字符串的**重复拼接**，而非截取前 32 字节
  - 实际派生的 key 不是"前 32 字符"，而是一个以 `secret` 循环填充的字符串
  - 注释说"HKDF-like"但代码不满足 HKDF 的任何安全属性（无盐、无伪随机函数）
- **修复建议**：
  1. 将 `getKey()` 改为：`Buffer.from(secret.slice(0, 32), 'utf8')`（显式截取）
  2. 或使用 `crypto.scrypt`/`crypto.pbkdf2` 做真正 KDF
  3. 代码中加注释说明为何这样做（兼容约束 / 性能 / 历史原因）
- **影响文件**：`src/lib/crypto.ts`（影响所有 API Key 加密解密）

### SEC-W-02：`$queryRaw` 统计查询存在隐式 SQL 注入风险（数据聚合层）

- **位置**：
  - `src/server/routers/news.ts:217, 230, 243, 256, 267, 275`
  - `src/features/daily-briefing/lib/collect.ts:107, 117`
  - `src/lib/news/service.ts:779`
- **类别**：2.1.2 注入攻击
- **证据**（news.ts analytics）：
  ```typescript
  prismaBase.$queryRaw<Array<{ date: string; count: bigint | number }>>`
    SELECT DATE(publishedAt / 1000, 'unixepoch', '+8 hours') as date, COUNT(*) as count
    FROM NewsItem
    WHERE deletedAt IS NULL AND publishedAt >= ${thirtyDaysAgo}
    GROUP BY DATE(publishedAt / 1000, 'unixepoch', '+8 hours')
  `;
  ```
- **风险评估**：
  - 当前参数 `thirtyDaysAgo` 是从 `Date.now()` 派生的常数，**无用户输入**，注入风险低
  - 但 `src/server/routers/news.ts:217` 中的 `confidence`/`sourceName` 字段是从查询参数传入
  - **最坏情况**：若未来有字段未做参数化直接拼入 SQL，攻击者可在 `category`/`source` 参数中注入
- **修复建议**：
  1. 全面审查所有 `$queryRaw`，确保所有变量均为 Prisma 参数化（`${variable}`）
  2. 禁止将用户输入直接嵌入 `$queryRaw` 字符串模板
  3. 将 `$queryRaw` 替换为 Prisma ORM 原生查询（groupBy + count + where 组合）
- **影响文件**：`src/server/routers/news.ts`, `src/features/daily-briefing/lib/collect.ts`

### SEC-W-03：cron 路由使用 Bearer token，但 token 在 env 中无过期机制

- **位置**：`src/app/api/cron/cleanup/route.ts:9-17`
- **类别**：2.1.1 硬编码敏感信息（间接）
- **证据**：
  ```typescript
  const secret = process.env.CRON_SECRET;
  const auth = req.headers.get('authorization');
  if (!secret || !auth || auth !== `Bearer ${secret}`) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
  }
  ```
- **风险**：
  - `CRON_SECRET` 是一次性生成的无过期机制的长字符串（`openssl rand -hex 32`）
  - 若泄露（git 提交 /.env 误提交 / 日志打印），攻击者可用它触发任意清理任务
  - `.env.example` 中已有 `CRON_SECRET="<openssl rand -hex 32>"` 占位示例，但仍需确保生产环境使用强随机值
- **修复建议**：
  1. 在 env.ts 中添加 `CRON_SECRET` 的最小长度校验（已通过 `z.string().min(16)` 约束）
  2. 建议在 `.gitignore` 中明确标注 `.env` 文件（已存在 ✅）
  3. 定期轮换 `CRON_SECRET`（建议写入 SOP 文档）
- **影响文件**：`src/app/api/cron/cleanup/route.ts`（以及所有 cron 路由）

- **位置**：`src/app/layout.tsx:55, 57` 和 `src/app/layout.tsx:63`
- **类别**：2.1.2 注入攻击（潜在）
- **证据**：
  ```typescript
  <script dangerouslySetInnerHTML={{ __html: PREPAINT_SCRIPT }} />
  <script dangerouslySetInnerHTML={{ __html: R2_BOOTSTRAP_SCRIPT }} />
  ```
- **分析**：
  - `PREPAINT_SCRIPT` 来自 `src/lib/bootstrap-script.ts`，是**硬编码常量**（无用户输入）
  - 内容仅包含 localStorage 读取 + CSS 变量写入 + 主题应用，无 HTML 注入点
  - 当前严重度：**低**（信任源 + 无用户输入）
- **建议**：保持现状，未来如需注入动态内容先经过 sanitize

### SEC-N-03：AI Key 创建时明文一次性返回（设计约束，非漏洞）

- **位置**：`src/server/routers/ai-keys.ts:130-134`
- **类别**：架构设计（明文显示策略）
- **证据**：
  ```typescript
  return {
    id: created.id,
    provider: created.provider,
    label: created.label,
    keyLast4: created.keyLast4,
    plainKey, // ⚠️ 明文只此一次返回
  };
  ```
- **分析**：
  - 这是**有意的设计决策**：AI Key 只在创建时返回一次明文，之后不再暴露
  - `plainKey` 本身不出现在 DB（只存 `keyHash` 和加密后的 `encryptedKey`）
  - 不属于安全漏洞，属于**用户体验权衡**
- **建议**：在 UI 侧明确提示用户"请立即复制，明文不再显示"
