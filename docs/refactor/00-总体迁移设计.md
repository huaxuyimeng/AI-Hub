# 00 · 总体迁移设计

> 唯一允许**跨模块描述**的文档。其他设计文档（`modules/*.md` `infra/*.md` `benchmark/*.md`）必须不跨越自身边界。
>
> 创建于 2026-09-06，配合 monorepo 重构 + 模块化治理。

---

## 1. 项目目标（一句话）

把当前的 `src/` 单体 Next.js 应用，改造为 **pnpm monorepo + 强模块边界 + 自动化治理** 的工程结构，使**新功能开发速度可衡量地提升**（不依赖个人记忆）、**Bug 修复影响面可控**、**模块可独立演进或下线**。

---

## 2. 范围

### 2.1 做什么

- **重构**：将 `src/` 单体迁移到 `apps/` + `packages/` monorepo
- **拆模块**：14 个业务模块各自独立封装（domain / interface / infra 三层）
- **立契约**：每个包暴露有限 `exports` 入口；跨包引用受 ESLint `no-restricted-imports` 约束
- **建文档体系**：调研报告 + 总体设计 + 模块设计 + 基础设施设计，分目录存放
- **建 skill / hook**：标准化高频任务（加 Provider、加 Parser、加 cron、修 Bug）
- **建归档机制**：超过有效期的设计文档/脚本自动归档，避免技术债堆积
- **建可观测性**：统一 logger + 分布式锁 + 关键路径 alert

### 2.2 不做什么

- ❌ **不改变业务功能**：迁移期间用户看到的界面、API 行为保持一致
- ❌ **不重写 UI**：UI 改造独立计划（`workbench-ui-designer` skill 驱动），不在本设计范围
- ❌ **不引入新数据库**：继续用现有 Prisma + SQLite(dev)/PostgreSQL(prod)
- ❌ **不切换 ORM**：保持 Prisma
- ❌ **不引入微服务**：仍是单一部署（Vercel + R2 + Upstash Redis）
- ❌ **不强行拆分数据**：多租户模型、schema 不重构，只调整代码组织
- ❌ **不写 E2E 测试**：本期不补 E2E（独立计划；可观测性 + 单元测试覆盖足够）

## 4. 依赖关系（顶层图）

> 箭头方向：**A → B** 表示 "A 依赖 B"。
>
> **约束**：下层模块**不感知**上层模块的存在（依赖只能向下）。

```
                          ┌──────────────────────────┐
                          │  apps/web (Next.js)      │  ← 唯一部署单元
                          └────────────┬─────────────┘
                                       │
        ┌──────────────────────────────┼──────────────────────────────┐
        │                              │                              │
   ┌────▼────┐              ┌──────────▼──────────┐         ┌─────────▼─────────┐
   │  chat   │              │    daily-briefing   │         │      其他页面      │
   └────┬────┘              └──────────┬──────────┘         └─────────┬─────────┘
        │                              │                              │
        │      ┌───────────────────────┼──────────────────────┐       │
        │      │                       │                      │       │
        │  ┌───▼────┐    ┌─────────────▼─────────────┐ ┌──────▼──────┐│
        │  │ ai-core│    │     slide-engine          │ │   theme     ││
        │  └────┬───┘    └───────────────────────────┘ └─────────────┘│
        │       │                                                  │
        │  ┌────▼─────────────────────────────────────┐             │
        └──┤  news / rankings / bilibili / discovery  ├─────────────┘
           └────┬─────────────────────────────────────┘
                │
        ┌───────▼─────────────────────────────────────┐
        │  packages/db  +  packages/observability       │  ← 基础设施
        │  (Prisma, logger, distributed-lock, alert)    │
        └──────────────────────────────────────────────┘
                │
        ┌───────▼──────────────────────────────────────┐
        │  packages/infra (auth / env / r2 / redis)     │  ← 跨切关注点
        └───────────────────────────────────────────────┘
```

### 4.1 依赖规则（强约束）

1. **业务模块只能依赖 `packages/db` `packages/observability` `packages/infra` 和比自己更"下"的业务模块**（按上面图）
2. **业务模块不得跨过 `slide-engine` 直接依赖 `daily-briefing` 的内部**（必须通过 `daily-briefing` 暴露的 `@aihub/daily-briefing/contracts`）
3. **任何包不得直接 `import` 另一个包的非 `exports` 字段**（ESLint 强制）
4. **`apps/web` 不允许反向依赖**：`apps/web` 可以被业务包 import（types only），但 `apps/web` 内部组件 import 业务包内部文件会被禁止

详见 [`infra/包契约规范.md`](./infra/包契约规范.md)。

## 8. 实施原则（红线）

1. **不写冗余代码**：每个新增文件必须有可演示的功能或可观测的改进
2. **不写"虚假代码"**：未使用即删除；TODO 必须有 owner + due date
3. **不自作主张**：每改一处先报告；任何超出本设计范围的修改先停
4. **优先安全**：跨租户、跨用户、跨角色的代码必须经过 `dependency-cruiser` + ESLint 双重约束
5. **小步前进**：每个 PR < 500 行 diff；每周一个 milestone
6. **可回滚**：每周末 tag；任何一步失败 git revert 不影响其他步
7. **文档与代码同 PR**：改 API 必须改文档；删代码必须删文档
